@AGENTS.md

## What this app is

SMW Job Plans: job cost estimating with a multi-step approval workflow, sitting as a middle layer in front of QuickBooks Online. Customers, jobs, actual costs, and invoices are imported from QuickBooks (read-only); plans are estimated, submitted, and approved here. Stack: Next.js 16 (App Router, deployed on Vercel) + Supabase (Postgres, Auth, RLS) + Tailwind CSS 4 + TypeScript (strict). Design docs: `docs/PLANNING.md` (product/architecture plan) and `docs/SPREADSHEET_REVIEW.md` (the Excel workbook the cost engine replicates, reverse-engineered column by column).

## Commands

```bash
npm install
npm run dev      # local dev server (needs .env.local — see README)
npm run build    # production build; also the de-facto type check
npm run lint     # eslint (flat config, eslint-config-next)
```

There is no test suite. `npm run build` is the main verification step.

Database migrations are plain SQL in `supabase/migrations/`, applied by pasting into the Supabase SQL editor or `supabase db push`. They are numbered and append-only: never edit an already-applied migration — add a new `NNNN_description.sql`.

## Architecture

### The database owns the business logic

Postgres is the source of truth for everything that matters; the UI is a thin layer over it:

- **Cost engine**: all derived numbers (weight, material/labor cost and price, consumables, overhead allocation, profit) are computed in SQL views — `plan_line_item_costs`, `plan_totals`, `plan_priority_totals` in `supabase/migrations/0001_initial_schema.sql`. Saved totals are never computed in TypeScript.
- **`src/lib/costing.ts` is a deliberate client-side mirror** of the `plan_line_item_costs` view so the plan editor (`src/components/plan/PlanWorkspace.tsx`) can show live totals while typing. Any change to the SQL cost math must be mirrored there (and vice versa) — they are verified to produce identical numbers.
- **Approval workflow**: the state machine (draft → submitted → approved/rejected/changes-requested) lives in SQL functions `submit_plan`, `approve_plan`, `reject_plan`, `request_changes`. These own the rules: TBD lines block approval, overhead is required before submit, creators can't approve their own plans, content locks outside draft states (`assert_plan_editable` + guard triggers), and every transition writes to `audit_log`. Server actions just call these RPCs.
- **Roles** (`admin`, `estimator`, `approver`, `viewer`) are enforced by RLS policies, not just the UI. The first user to sign up becomes admin (`handle_new_user`).
- **Approval thresholds are data**, not code (`approval_thresholds` table; default <$25k = 1 approval, $25k–$100k = 2, >$100k = 3).

### Three Supabase clients — pick the right one

- `src/lib/supabase/server.ts` — anon key + user cookies, for Server Components and server actions (RLS applies).
- `src/lib/supabase/client.ts` — browser client for client components.
- `src/lib/supabase/service.ts` — service role, **bypasses RLS**, `import "server-only"`. Used by the QuickBooks sync/OAuth routes — it's the only thing that can touch `qb_connections` (RLS deny-all) and write imported QB data — and by the admin-gated Financials reads (see General ledger below).

### Auth flow

`src/proxy.ts` (Next 16's successor to `middleware.ts`) refreshes the Supabase session on every request and redirects unauthenticated users to `/login`. Public paths are listed in `PUBLIC_PATHS` there. Pages under `src/app/(app)/` additionally call `requireUser()` from `src/lib/auth.ts` to get `{ supabase, user, profile }`.

### Route/mutation conventions

- Authenticated UI lives in the `src/app/(app)/` route group; `/login`, `/eula`, `/privacy` are public.
- Mutations are server actions in a colocated `actions.ts` per route (e.g. `src/app/(app)/plans/actions.ts`), validated with Zod, returning `{ ok: true } | { ok: false; error }`. Postgres `raise exception` messages are stripped to a user-facing string via the shared `fail()` helper pattern.
- File exports (CSV, Excel via `exceljs`) are route handlers under `src/app/api/export/`.

### QuickBooks integration

- `src/lib/quickbooks.ts` — OAuth2 (token exchange/refresh) and all import logic. Route handlers under `src/app/api/qb/` (connect, callback, sync, disconnect).
- **Multi-company**: one connection per QB company (realm); imported rows are tagged with `realm_id` because QB record IDs are only unique within a realm (migration `0003`).
- Actual costs (`job_costs`: Bill/Purchase/VendorCredit lines + JournalEntry lines + TimeActivity valued at the internal labor rate; vendor credits and credit-card credits (`Purchase.Credit`) are stored negative, and since migration `0036` bill/purchase lines carry `qb_account_id` / `account_classification` — an item line's account is its item's purchase account, the inventory asset for stock items) and invoiced revenue (`job_invoices`) are imported per job. The books are audited through 2024-12-31, so each sync **refreshes only the import window (delete + insert scoped to `txn_date >= JOB_COSTS_START_DATE`, currently `2025-01-01`)** in `src/lib/quickbooks.ts` — rows dated earlier are frozen history that persists in Supabase and is never deleted or re-fetched.
- That import window must reach back at least as far as `NO_TXN_CUTOFF` in `src/lib/jobViews.ts` — the "No Transactions" dashboard view depends on it.
- **Nightly sync**: `/api/cron/qb-sync` (Vercel cron, `vercel.json`) runs the whole import — jobs *and* financials — every morning at `QB_SYNC_HOUR` (default 4) local time in `QB_SYNC_TIMEZONE` (default `America/New_York`). It can't be one request: a single invocation caps at 300s, so migration `0024` models each morning as a **run** of ordered **steps** (`customers_jobs`, `job_costs`, then one `general_ledger` step per connected realm) and the route is a worker — every tick claims steps it can finish, later ticks drain the rest. Postgres owns the invariants (`begin_qb_sync_run` / `claim_qb_sync_step` / `finish_qb_sync_step`): one scheduled run per org per *local* date, at most one step running anywhere (steps rotate the QB refresh token — two at once can strand a connection), steps in `position` order, and stale-step revival with three attempts. Because Vercel cron is UTC-only the schedule is a UTC *window* and `localClock()` in `src/lib/qbSyncSchedule.ts` decides when the run starts, which keeps 4 AM at 4 AM across DST; move the `vercel.json` window if the hour/timezone changes. The route authenticates with `CRON_SECRET` and is exempt from the proxy's session redirect via `PUBLIC_PATHS`.
- **General ledger**: `syncGeneralLedger` imports the chart of accounts (`gl_accounts`) and every posted ledger line (`gl_lines`) via the QBO GeneralLedger *report* API (quarter-sized windows since `FINANCIALS_START_DATE`, currently `2025-01-01`), so QuickBooks does the double-entry expansion — never reconstruct postings from raw entities. The Reports API caps a response at 400,000 cells and signals overflow only by cutting the report short (an "Unable to display more data" row) — and since the report runs in chart order, the cut silently drops the last accounts (other income/expense, e.g. interest). `parseGlReport` flags that, and `fetchGeneralLedgerLines` halves any truncated window until each piece fits; never ingest a report without that check. Pre-2025 ledger lines are frozen audited history: migration `0020` marks them `archived`, `gl_line_facts` shows them outside the sync's generation scheme, and `prune_gl_lines` skips them, so syncs can't drop or duplicate them. Amounts are natural-signed (positive increases an account in its normal direction). **Every Financials report (pivot, Income Statement, Ratios, Reconciliation, Budget) shows the ledger as booked so it ties to QuickBooks: no intercompany eliminations below Net income (intercompany activity is handled on the balance sheet, so that income is only counted once) and no allocations between categories (the Employee Benefits → Direct Costs reclassification was removed; a replacement approach is planned).** The Financials page (`src/app/(app)/financials/`) slices them through the `gl_pivot` SQL function (migration `0009`); aggregation stays in Postgres. Cell drill-downs list raw lines via `gl_lines_detail` (migration `0010`), whose dimension CASE expressions must stay in lockstep with `gl_pivot`; shared dimension/scope vocabulary lives in `src/lib/financials.ts`. GL data is admin-only: the Financials pages/export verify the caller with `requireAdmin()` and then read via the service-role client — RLS on `gl_accounts`/`gl_lines`/`gl_sync_state` checks `is_admin()` (migrations `0014`/`0015`) to block direct API access, but its qual makes `gl_pivot`-sized queries blow the statement timeout, so the app's own read path bypasses it after the role check. The Chart of Accounts page (`/financials/accounts`) assigns a user-owned `category` per account (migration `0019` — the sync upsert's column list never touches it), which the expandable Income Statement (`/financials/statement`, assembled by `buildCategoryStatement` in `src/lib/financials.ts`) uses to group Revenue/Expense accounts. The Income Statement shows one QuickBooks class at a time from a Class dropdown (`?class=`, default All classes; months are the default columns and classes are never columns): it and its export read account × month × class cells through `loadStatement` in `src/lib/statementServer.ts` (via `budget_ledger_summary`), so All classes is exactly the sum of the classes. The Reconciliation page (`/financials/reconciliation`) verifies the imported ledger ties to QuickBooks: upload the consolidated P&L Excel export (monthly columns) and `src/lib/reconciliation.ts` parses it (`parsePlWorkbook`), truncates it at the last complete month (`omitMonthsAfter` — the in-progress month is omitted across all Financials views and never enters the tie-out), and diffs it account × month against `gl_pivot` cells (`buildReconciliation`) — both sides natural-signed, so amounts compare with no sign flipping. The tie-out is per **detail account**, never by the app's categories or by parent rollups: the parser rebuilds each export row's full "Parent:Sub" path from QuickBooks' header / "Total for …" group pairs (only QB's own statement sections are sections) and matches it to `gl_accounts.fully_qualified_name`, falling back to the account's own name only when that name is unique among the unmatched rows on both sides; an export with sub-accounts collapsed is flagged with a warning. Neither side is adjusted, so every account and net income should tie to the cent. The page action and the Excel export (`/api/export/reconciliation`, a POST that re-uploads the same file) share the file → result pipeline in `src/lib/reconcileServer.ts`.

### Budget

`/financials/budget` (admin-only, sidebar Budget and Forecast → Budget) is a calendar-year budget (`BUDGET_YEAR` in `src/lib/budget.ts`, currently 2027) in the Income Statement's layout. Baseline = each account's actuals for the twelve months ending June 30 of the prior year (`baselineRange`), read in one ledger scan by `budget_ledger_summary` (migration `0027`, one JSON row — paged `gl_pivot` calls per company timed the page out; `0034` adds each cell's QuickBooks class as a seventh tuple element; `0035` scopes it to the org so `gl_lines_date_idx` range-scans just the window instead of the whole ledger — any new ledger read must do the same) and mapped month-for-month onto the budget year, then grown by per-company growth assumptions: each account at its own company's rate for its `gl_accounts.category` (`budget_category_assumptions`, migration `0028`, keyed by classification + category label), falling back to the company's revenue / expense default (`budget_assumptions`, migration `0026`; direct costs use the expense default) for categories with no rate and for uncategorized accounts. Growth looks categories up in each realm's own account map (`realmCategories`), not the consolidated display map. `save_budget_assumptions` writes a company's defaults and its whole category set in one transaction (service-role only). New initiatives (`budget_initiatives` + `budget_initiative_lines`) carry expected amounts per account for the budget year, spread evenly from a start month through an end month (`end_month`, migration `0029`; `spreadInitiativeLine` is the one spread both the budget and the exports use); they fold into the budget **only when `status = 'approved'`** — proposed/rejected ones are listed but excluded, and guard triggers lock an initiative's lines and its start/end months unless it is proposed. Initiatives export by month via `/api/export/budget-initiatives` (`?id=` one initiative, else `?company=` all in view; initiative tables only, no ledger read) and as the budget workbook's *Initiatives by month* sheet — both written by `writeInitiativesByMonth` in `src/lib/budgetInitiativeSheet.ts`. An admin can also type figures straight into the budget statement's account cells (single company, Budget view): a month, or an account's annual Total, which `respreadTotal` re-spreads in the months' current shape. Each typed month is a row in `budget_account_overrides` (migration `0031`, keyed by account full name × class × month since `0034`; `set_budget_account_overrides` replaces one account × class's set, service-role only) that replaces that account-class-month's growth-based amount in `accountBaseMonths` / `growBaselineCells` — growth edits no longer move it, and approved initiatives still add on top. Typed figures autosave per cell (`saveAccountOverrides`), so the export reads the saved set (plus a *Typed figures* sheet); `StatementTable` takes an optional `editor` for this and is otherwise unchanged on the Income Statement. The growth % fields are plain text (no spinner arrows). **The budget is built per QuickBooks class and rolls up** (migration `0034`): every baseline cell (`BudgetCell` = `PivotCell` + `class_name`), typed figure, and initiative (`budget_initiatives.class_name`, locked like its months unless proposed) carries a class keyed exactly as `gl_pivot` keys its class dimension (`NO_CLASS` = `'(no class)'`), `assembleBudget` takes a `cls` filter (null = All classes), and a company's budget is the sum of its classes and All companies the sum of the companies — never computed separately. Growth rates stay per company and apply to every class. The page's Class filter (`?class=`) scopes the statement, tiles, initiatives, and exports; typing needs one company and one class (or a company with a single class). On All classes the page sends the browser cells merged across classes (`mergeClasses`; accounts with typed figures stay split), so the default view costs no more than before classes. A failed load renders as a banner via `budgetLoadErrorMessage` (e.g. a missing migration), not a 500. `0034` split pre-existing whole-account typed figures across each account-month's baseline classes pro-rata, so no total moved. `src/lib/budget.ts` re-keys everything into synthetic `PivotCell`s so `buildCategoryStatement` assembles the budget exactly like the statement; Budget vs Actual feeds full-year budget, YTD budget, and YTD actual as three columns of one statement. The page (`BudgetWorkspace`, client-side so growth edits re-price live; nothing is stored until Save changes) and the Excel export (`/api/export/budget`, which carries the on-screen rates as `growth=<realm>:<rev>:<exp>` and `cgrowth=<realm>:<R|E>:<pct>:<category>` params — `budgetExportHref` / `assumptionsFromParams` own that format; on All companies it writes the consolidated tab then one tab per company, each assembled like that company's own view — its categories) share the server loader `loadBudget` in `src/lib/budgetServer.ts` and the assembly `assembleBudget` in `src/lib/budget.ts`, so the file always matches the screen. The workbook itself is written by `buildBudgetWorkbook` in `src/lib/budgetWorkbook.ts` (request parsing + admin check in `budgetExportContext`), shared by `/api/export/budget` and `/api/export/budget-classes` (a zip of one workbook per class, for distributing class budgets); a single company on All classes gets one tab per class after the company tab. On All companies the page's *Export a company…* picker downloads one company's standalone workbook — the same route with `company=<realm>` and only that company's on-screen rates — whose statement is identical to that company's tab in the All companies workbook; on All classes *Export a class…* downloads one class's workbook (`class=<class>`) or the per-class zip. Files are named after the company and class.

### Barge Program

New-build deck barge quoting (`src/app/(app)/barge/`) reuses the plan blueprint one-for-one: inputs live in `barge_configs` / `barge_quotes` / `barge_quote_steel_lines` / `barge_quote_labor_phases`, all derived numbers live in the SQL views `barge_quote_steel_line_costs` and `barge_quote_totals` (migration `0017`), and the same draft → submitted → approved workflow runs through `submit_barge_quote` / `approve_barge_quote` / `reject_barge_quote` / `request_barge_quote_changes` — sharing `approval_thresholds` (evaluated against the quote's **sales price**), guard-trigger edit locking, and `audit_log` (`entity_type = 'barge_quote'`). `src/lib/barge.ts` is the deliberate client-side mirror of those views (same contract as `costing.ts`) and also holds the parametric rough-quote model (geometry → plate weight, TSG-calibrated allowance/framing factors) and the two reference takeoff templates. The quote workbench saves content wholesale (header update + delete/re-insert of lines and phases) rather than per-row. Excel exports live in `src/lib/bargeWorkbook.ts`: `/api/export/barge-quote?id=` (one saved quote, one sheet) and `/api/export/barge-quotes` (an All Quotes summary, then that same sheet per quote) read the SQL cost views and never re-price; `/api/export/barge-rough` carries the Rough Quote Builder's on-screen inputs as params (`roughExportHref`) and re-prices them with `parseConfigValues` + `computeRoughQuote`, the builder's own rules, so the file matches the screen. The builder's field list (`CONFIG_FIELD_GROUPS`), build-up rows (`roughBuildUp`), and the workbench's sensitivity grid (`marginSensitivity`, `sensitivityColor`) live in `src/lib/barge.ts` so screen and file share one definition.

### Capitalized Labor

`/capitalized-labor` lists journal-entry labor on non-billable (EQP) and intercompany jobs (job bucketing: `capLaborBucket` in `src/lib/capitalizedLabor.ts`). It is viewed for **one period at a time — a calendar year, a single month, or a from/to month range** (default: the current year to date; history back to Jan 2023; UTC dates, never past today). The URL is the state (`?year=2025`, `?month=2026-03`, `?from=2025-07&to=2026-06`; a range beats a month beats a year, anything invalid falls back to the default), and `capLaborPeriod` in `src/lib/capitalizedLabor.ts` is the one parser: the page, its job drill-down (the server action re-parses the page's params), both exports (`capLaborPeriodFromSearch`; download links carry the same params via `capLaborHref`), and the Already Capitalized page and export all filter by the window it returns, so screen and file always match. `PeriodPicker` (`src/app/(app)/capitalized-labor/`) is the shared year-pills / month / range control (plain links and GET forms). For multi-month periods both pages show a **By month** card and their workbooks a *By Month* sheet — `capLaborByMonth` (dashboard; follows the active tab on screen, all candidates in the file) and `capScheduleByMonth` (Already Capitalized) — and each month row links to that month alone. The benefit allocation column is read straight from `job_benefit_allocation_cache` for the period's months (month-grain, so a partial month counts in full). Which journal lines count, and how, lives only in the SQL view `cap_labor_lines` (migration `0030`), which the page, its line drill-down, and both exports read: **wages and the employer's share of payroll taxes count; withholdings from the employee's check — and every other payroll liability — never do** (expense-side accounts only, judged by `job_costs.account_classification`; lines whose account doesn't match the chart fall back to a name test). A counted line is *capitalized* only when its journal entry debits a Fixed Asset / Other Asset account (`job_costs.je_debits_asset`) — the asset varies by equipment and job, so detection is by account type, never name; everything else is *labor posted*, net of reversals. `syncJobCosts` stores those account facts per journal line (`isCapitalAssetAccount` in `src/lib/quickbooks.ts`); migration `0030` backfilled frozen pre-2025 rows from `gl_accounts` / `gl_line_facts` with the same rule. The labor-account test itself is one SQL function, `cap_labor_account(name, classification)` (migration `0032`), used by `cap_labor_lines` and by the **Already Capitalized** schedule (`/capitalized-labor/already-capitalized`, sidebar Capitalized Labor → Already Capitalized, admin-only because it reads the ledger): `capitalized_labor_entries(p_from, p_to)` (migration `0032`; `0033` scopes it to the org so `gl_lines_date_idx` range-scans just the window instead of the whole ledger) returns, as one JSON row, every general-ledger line of the journal entries that debit a Fixed Asset / Other Asset account and, net, credit labor — so it also catches capitalization credits with no job tag — and `src/lib/alreadyCapitalized.ts` shapes them into entries and a by-asset rollup (labor split pro-rata when an entry debits several assets) for both the page and its export (`/api/export/already-capitalized`, shared loader `loadCapSchedule`). It takes the same period selection as the dashboard (`capLaborPeriod`); a long range reads more of the ledger, and a timeout renders as a banner via `capScheduleErrorMessage`.

### Capitalized Materials

`/capitalized-materials` (sidebar Capitalized Labor → Capitalized Materials, all signed-in users) lists everything **expensed on non-billable jobs in every QuickBooks company** — EQP equipment jobs and Precision Paint's own PPS jobs, the Jobs dashboard's Non-Billable rule minus its recency test (`capMaterialBucket` in `src/lib/capitalizedMaterials.ts`; transportation never qualifies). Which lines count lives only in the SQL view `cap_material_lines` (migration `0036`): bill, purchase and vendor-credit lines whose account is on the expense side (unknown counts — frozen item lines can't be traced), plus journal lines on a non-payroll expense account (`cap_material_account` = expense and **not** `cap_labor_account`, so no dollar is on both Capitalized pages); time entries never count. A journal line is *capitalized* when its entry debits a Fixed Asset / Other Asset account (`je_debits_asset`, same rule as labor), everything else *expensed*; awaiting review = expensed − capitalized. Expensed splits into Materials (item lines), Outside labor (bill/purchase on a labor item/account), and Other (`capMaterialKind`). It takes Capitalized Labor's period (`capLaborPeriod`, `PeriodPicker`) and `?tab=equipment|internal`. The page, its job drill-down (`getCapMaterialLines`), the CSV (`/api/export/capitalized-materials`) and the workbook (`/api/export/capitalized-materials-workbook`: Jobs, By Company, By Month, Expense Lines) all read through `loadCapMaterials` in `src/lib/capitalizedMaterialsServer.ts` — which reads lines only for the non-billable jobs, 100 job ids per request on `job_costs_job_date_idx` — and roll up with the helpers in `src/lib/capitalizedMaterials.ts`, so screen and file match. Pre-2025 frozen rows predate vendor-credit import and refund signing, so 2023–2024 figures are an upper bound (the page's methodology says so).

### Jobs dashboard classification

`src/lib/jobViews.ts` buckets every job into exactly one of five views (Customer Jobs, Transportation, Intercompany, Non-Billable, No Transactions). The dashboard tabs (`src/app/(app)/jobs/`) and the Excel workbook export (`src/app/api/export/jobs-workbook/`) must bucket identically, so the rules live only here:

- Job-number suffix `LH`/`HS`/`FL`/`BC` → Transportation; prefix `EQP` → Non-Billable; jobs in the Precision Paint QB company under the `PPS` customer → Non-Billable (internal self-work).
- Sister-company customers (fuzzy name matching in `src/lib/enterprise.ts`) → Intercompany.
- No cost/invoice activity since `NO_TXN_CUTOFF` → No Transactions (US Army Corps of Engineers jobs are exempt and stay under Customer Jobs).

The dashboards' Benefit allocation column (Jobs and Capitalized Labor, plus their workbook exports) comes from the `job_benefit_allocation_months` view (migrations `0021`/`0022`; `job_benefit_allocation_totals` is its all-time/YTD/MTD rollup): per QB company × month it computes the employee-benefits allocation — Employee Benefits × Direct Labor ÷ (Direct Labor + Salaries & Wages), matched via `gl_accounts.category` and account names — and distributes it across that company's jobs pro-rata by direct-labor cost. It once mirrored an Income Statement reclassification that has since been removed, so this view is now the allocation's only definition; the views are intentionally **not** `security_invoker` so they can aggregate the admin-only `gl_lines` while exposing only per-job dollars to all signed-in users. Deriving the allocation is far too slow for a page load — even one evaluation blows the authenticated role's statement timeout, and a bigger timeout is not available to browser-facing roles (`statement_timeout` is armed before a function's own `SET` applies, see migration `0012`) — so **nothing reads it live**: migration `0025` materializes the month view as `job_benefit_allocation_cache` and points every reader at it (`job_benefit_allocation_totals` for the Jobs dashboard; the Capitalized Labor page and its workbook read the cache's job × month rows for the selected period directly — `job_benefit_allocation_summary(p_from, p_to)` from migration `0024` also reads the cache but is no longer called by the app). The cache is rebuilt by `refresh_job_benefit_allocation()` — granted to `service_role` only, wrapped by `refreshBenefitAllocation()` in `src/lib/benefitAllocation.ts` — at the three moments its inputs move: a jobs/costs sync, a ledger sync, and an account's category changing. Anything else that can change those inputs must refresh it too, or the dashboards go stale.

## Conventions

- Path alias `@/*` → `./src/*`.
- Shared row/domain types are in `src/lib/types.ts`; small shared UI primitives in `src/components/ui.tsx`.
- Env access goes through `src/lib/env.ts` (accepts both `NEXT_PUBLIC_SUPABASE_*` and the Vercel Marketplace add-on's `SUPABASE_*` names). QuickBooks env vars: `QB_CLIENT_ID`, `QB_CLIENT_SECRET`, `QB_ENVIRONMENT` (`production` is the default — sandbox must be explicit), `NEXT_PUBLIC_APP_URL` (OAuth redirect).
- Server-only modules that hold secrets start with `import "server-only"`.
