# QuickBooks sync

How customers, jobs, actual costs and invoices are imported from QuickBooks Online, how the nightly sync is scheduled and serialized, and how its health is shown. The general ledger import has its own page: [general-ledger.md](general-ledger.md).

Code: `src/lib/quickbooks.ts`, `src/lib/qbSyncSchedule.ts`, `src/lib/syncHealth.ts`, `src/lib/syncAlert.ts`, `src/app/api/qb/`, `src/app/api/cron/qb-sync/`.

- `src/lib/quickbooks.ts` — OAuth2 (token exchange/refresh) and all import logic.
  - Route handlers under `src/app/api/qb/` (connect, callback, sync, disconnect).
- **Multi-company**: one connection per QB company (realm); imported rows are tagged with `realm_id` because QB record IDs are only unique within a realm (migration `0003`).
- **Connection health**: only Intuit refusing the refresh token outright (`invalid_grant`, a permanent `QbTokenError`) marks a `qb_connections` row `error`; network failures and 5xx leave it `connected` and throw so the step retries.
  - `getValidConnections` retries `error` rows on every sync (a refresh that works puts them back to `connected`) and leaves out only the companies Intuit still refuses; `planSteps` keeps their ledger step so the run ends *Completed with errors* instead of silently omitting a company.
  - `/api/qb/callback` requires admin, like `/api/qb/connect`.
- Actual costs (`job_costs`: Bill/Purchase/VendorCredit lines + JournalEntry lines + TimeActivity valued at the internal labor rate; vendor credits and credit-card credits (`Purchase.Credit`) are stored negative, and since migration `0036` bill/purchase lines carry `qb_account_id` / `account_classification` — an item line's account is its item's purchase account, the inventory asset for stock items) and invoiced revenue (`job_invoices`) are imported per job.
  - The books are audited through 2024-12-31, so each sync **refreshes only the import window (`txn_date >= JOB_COSTS_START_DATE`, currently `2025-01-01`, defined in `src/lib/businessRules.ts`)** in `src/lib/quickbooks.ts` — write first, clear second (`refreshImportWindow`: upsert every fetched row on its QuickBooks key stamped with the sync's `last_synced_at`, then delete the window's rows that stamp didn't touch), so a sync that dies partway never leaves a company's costs or invoices missing and a transaction re-dated from 2024 into the window updates its frozen row instead of colliding with it — rows dated earlier are frozen history that persists in Supabase and is never deleted or re-fetched.
- That import window must reach back at least as far as `NO_TXN_CUTOFF` in `src/lib/jobViews.ts` — the "No Transactions" dashboard view depends on it.
- **Nightly sync**: `/api/cron/qb-sync` (Vercel cron, `vercel.json`) runs the whole import — jobs *and* financials — every morning at `QB_SYNC_HOUR` (default 4) local time in `QB_SYNC_TIMEZONE` (default `America/New_York`).
  - It can't be one request: a single invocation caps at 300s, so migration `0024_scheduled_qb_sync.sql` models each morning as a **run** of ordered **steps** (`customers_jobs`, `job_costs`, one `general_ledger` step per realm, one `balance_sheet` step per realm — migration `0043`, the prior month end's balance sheet — then `benefit_allocation` — migration `0037` — which rebuilds the benefit-allocation cache those imports feed) and the route is a worker — every tick claims steps it can finish, later ticks drain the rest.
  - Postgres owns the invariants (`begin_qb_sync_run` / `claim_qb_sync_step` / `finish_qb_sync_step`): one scheduled run per org per *local* date, at most one step running anywhere (steps rotate the QB refresh token — two at once can strand a connection), steps in `position` order, and stale-step revival with three attempts.
  - Because Vercel cron is UTC-only the schedule is a UTC *window* and `localClock()` in `src/lib/qbSyncSchedule.ts` decides when the run starts, which keeps 4 AM at 4 AM across DST; move the `vercel.json` window if the hour/timezone changes.
  - **Month-end run**: a second cron window in `vercel.json` covers midnight on the 1st of each month. A tick in the first hours of the 1st local time (`isMonthRollover` in `src/lib/balanceSheet.ts`) starts a `trigger = 'month_end'` run of `balance_sheet` steps (`beginMonthEndRun`; one per org per local date), so the Balance Sheet page shows the month that just closed without waiting for the nightly sync. The worker drains it like any other run. It is not "the nightly sync": the Settings card and sync health read `trigger = 'scheduled'` only. Move this window too if the timezone changes.
  - The route authenticates with `CRON_SECRET` and is exempt from the proxy's session redirect via `PUBLIC_PATHS`.
  - **Manual syncs go through the same queue** (migration `0039`, `runManualSync` in `src/lib/qbSyncSchedule.ts`): each button press is a `trigger = 'manual'` run whose steps the request claims by run id, so it can never overlap the nightly run or another manual one (it gets a 409 "another sync is running" instead); a manual step never retries and never stays queued.
  - **Sync health is shown on every page** by the app layout (`loadSyncHealth` in `src/lib/syncHealth.ts`, service-role read of succeeded steps): a "QuickBooks data as of" stamp for everyone, and for admins a banner when the last nightly run failed, no run has started in 36 hours, a connection is in error, or an import is over a day old.
  - When a nightly step uses its last retry, `alertSyncFailures` (`src/lib/syncAlert.ts`) also posts to `QB_SYNC_ALERT_WEBHOOK_URL` if that is set (Slack/Teams-style `{ text }` webhook).
